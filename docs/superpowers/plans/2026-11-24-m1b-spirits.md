# M1b Spirits Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A question a villager refused to invent an answer to can be answered, by the spirits (an AI, checked against the culture) or by the owner as the shaman; the answer joins the culture, and the villager tells it and says who gave it.

**Architecture:** The culture format gains a third origin for an entry, "consult". `@fieldwork/villagers` gains `askSpirits`: one model call for an answer, a rule check, one model call for a contradiction check, and a pure function that adds the resulting entry to a copy of the culture. The trial page saves each outcome in a new `consults` collection, rebuilds each culture from the base file plus the saved answers, and offers the controls under a refusal. `tools/checks` gains a fifth check that runs the whole path.

**Tech Stack:** as M1a: TypeScript 6, zod 4, Vitest, React, Vite single-file build, Playwright 1.63.0, the gateway's fake and login providers, the claude.ai page runtime (`sample`, `db`).

**Spec:** `docs/superpowers/specs/2026-11-24-m1b-spirits-design.md`. Parents: `docs/superpowers/specs/2026-11-24-m1a-villagers-design.md`, `docs/superpowers/specs/2026-11-23-fieldwork-game-design.md` sections 5.3, 5.4 and 9.3.

## Global Constraints

- English only; both cultures are invented; no API key and no server.
- `@fieldwork/villagers` depends only on `@fieldwork/contracts`. `apps/client` depends on neither it nor the gateway.
- Nothing a model wrote joins a culture, is shown or is saved as an answer before both checks have passed. A failed or unreadable check keeps nothing. No model call is retried automatically.
- The spirits never say what anything stands for or means, never put a guarded entry into other words, and never mark an answer "never said".
- A spirit answer is always marked as the spirits'. The words "The shaman was silent. The spirits spoke." are written by the page, not by a model.
- The question carried to the spirits is data: it reaches a model only inside a marked block with `<` replaced by `‹`, and never appears in a villager's standing instructions.
- For the sealed culture before reveal, the text of an added entry, a discarded spirit answer and the reasons for a silence are not shown anywhere.
- Model output is set as text, never as HTML.
- Calls through the login provider stop at 600 in total; 497 are used.
- Everything in `CLAUDE.md` still applies. Test snippets omit imports and give paths from the repository root.

## Review Focus

1. The spirits return something other than the JSON asked for, or the check's verdict lacks a list: nothing joins the culture, the question stays open, and the page says the spirits did not answer in a way it could read. (Tasks 2, 4)
2. The question is hostile text, raised when a reply to "ignore your instructions…" was caught: it reaches the spirits only as marked data, and it never becomes a topic in any villager's instructions. (Task 2)
3. A saved outcome no longer fits (a damaged entry, a villager who is gone, an entry id already taken): it is skipped, the page loads, and the rest is kept. (Task 3)
4. The owner presses "Ask the spirits" while a reply or another consult is on its way, or the same question was refused twice: one outcome, one entry. (Task 4)
5. Claude cannot be reached during a consult (consent declined, rate limit, signed out): a plain message, nothing saved, the button still there, nothing retried by itself. (Task 4)

```ts
export type AskPurpose = "answer" | "check" | "judge" | "spirits" | "spirits_check";

/** A question a villager refused to invent an answer to. */
export interface Consult { villagerId: string; question: string; visitorLine: string }

export const SPIRIT_KINDS = ["answer", "people_disagree", "not_spoken_of", "already_settled", "no_answer"] as const;
export type SpiritKind = (typeof SPIRIT_KINDS)[number];
export const SPIRIT_STATEMENT_WORDS = 60;
export const SPIRIT_TOPIC_WORDS = 12;

export interface SpiritDraft { kind: SpiritKind; statement: string | null; topic: string | null;
  entryKind: EntryKind | null; say: Say | null; entries: string[] }
export interface SpiritVerdict { contradicts: string[]; explains: string[]; unfit: string[] }

export function parseSpiritDraft(value: unknown): SpiritDraft | null;
export function parseSpiritVerdict(value: unknown): SpiritVerdict | null;   // null unless all three lists are there
export function checkSpiritByRule(culture: Culture, draft: SpiritDraft): string[];   // reasons; empty means it passes
export function buildSpiritRequest(culture: Culture, consult: Consult, model: ModelClass): AskRequest;       // purpose "spirits"
export function buildSpiritCheckRequest(culture: Culture, consult: Consult, draft: SpiritDraft): AskRequest; // purpose "spirits_check", model "balanced"

export type SpiritOutcome =
  | { status: "answered"; entry: CultureEntry; culture: Culture }
  | { status: "settled"; entries: string[] }
  | { status: "silent"; reasons: string[]; discarded?: string };

/** Rejects with VillagerTurnError, keeping nothing, when the answer or the verdict cannot be read. */
export function askSpirits(deps: { ask: Ask }, input: { culture: Culture; consult: Consult; model: ModelClass }): Promise<SpiritOutcome>;

/** The entry for an answer, with the next free id of the form c1, c2, … */
export function consultEntry(culture: Culture, consult: Consult,
  answer: { by: "shaman" | "spirits"; statement: string; topic: string; kind: EntryKind; say: Say }): CultureEntry;
/** A copy of the culture with the entry added and known to the villager who asked. Null if the entry is not from a consult, its id is taken, or that villager is not there. */
export function addConsultEntry(culture: Culture, entry: CultureEntry): Culture | null;
```

Behaviour the signatures do not settle:

- `parseSpiritDraft`: an object with a known `kind`; `statement` and `topic` trimmed text or null; `entryKind` one of `ENTRY_KINDS` or null; `say` one of the three or null; `entries` a list of text, missing counts as empty, any other type is unreadable.
- `checkSpiritByRule`, for `answer`, `people_disagree`, `not_spoken_of`: statement present, one line, at most 60 words; topic present, one line, at most 12 words; every id in `entries` exists; `say` is not `shown`; `entryKind` is not `symbol_meaning` or `opposition`; the statement contains no `earned` or `shown` entry's statement word for word (case and spacing ignored). For `already_settled`: `entries` is not empty and every id exists. For `no_answer`: nothing.
- `askSpirits`: `no_answer` is `silent` with the reason `the spirits gave no answer`, with no second call. `already_settled` that passes the rule is `settled`, with no second call. A rule failure is `silent` with the reasons and `discarded` set to the statement, with no second call. Otherwise the check call; any finding is `silent` with reasons prefixed `contradicts the culture: `, `says what something means: `, `does not fit: `; none is `answered`.
- The entry made from a spirit answer: `answer` uses the draft's `entryKind` (missing counts as `fact`) and `say` (missing counts as `anyone`); `people_disagree` is kind `fact`, say `anyone`; `not_spoken_of` is kind `prohibition`, say `anyone`.
- `buildSpiritRequest`: instructions hold the land, every myth in full, every entry as `- [id] (kind; topic; anyone may say it | not for a stranger | never said aloud) statement`, the customs, and who lives there; never the culture's `silences`. The single user turn holds `<asked_by>`, `<question>` and `<visitor_line>` blocks with `<` replaced by `‹`.
- `buildSpiritCheckRequest`: the same record of the culture; the user turn holds `<question>` and `<new_statement>`.
- In `requests.ts`: an entry whose origin is a consult is listed for a villager with its provenance after the statement, `(the spirits' answer, given when the shaman was silent)` or `(the shaman's own answer)`; the consult's question text is never included. `ANSWER_RULES` gains rule 11 (say who gave such an answer; never call the spirits' answer the shaman's). `CHECK_RULES` allows saying that the shaman or the spirits gave an answer the sources mark as theirs, and reports as unsupported a reply that credits the shaman with the spirits' answer. In the check's sources a cited consult entry carries the same provenance.

- Every culture on the page is `withAdditions(base, saved.consults)`.

- "What is true here" marks an added entry "from the spirits" or "from the shaman" and offers "Withdraw", with a confirmation, which removes the saved outcome.

- The footer says that asking the spirits is two more requests.
